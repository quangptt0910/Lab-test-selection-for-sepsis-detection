# ADR-0008: Experiment runner

Status: accepted (M3-1). Code in `sepsis.eval.{experiment_config,tables,runner,run_experiment}` and `sepsis.risk.base`.

## Context
Every risk-model experiment (B0–B3, ablations) must be run, scored and logged the same way under the three setups of ADR-0004. The pieces existed (split helpers, the view, the feature builder, the U1 − U0 target, the scorer and threshold tuning, ADR-0007), but nothing joined them, and several choices were open: which view a model is fitted and scored on, how a model plugs in, where results go, and what a partial run means. Building the view, features and targets for all dev patients took about 2.3 min per experiment, most of it the same work each time.

## Decision
1. **One command.** `uv run python -m sepsis.eval.run_experiment configs/<name>.yaml [--allow-dirty] [--no-cache]`. The `run-experiment` skill runs its pre-flight checks, calls this command, then compares the new LOG row with earlier ones.
2. **Strict config schema.** Required: `id, hypothesis, seed, split.setups, features.hand_crafted, features.lab_masking_p, features.signatures (null, or signature block names from the `signatures` section of `configs/features.yaml`, M4-1), target, model.type, model.params, note`. Unknown keys are refused. The threshold grid is not an experiment setting: it comes from `configs/eval.yaml`.
3. **Which view for what.** Models are fitted on features from the **training view** (as recorded, panel-draw masking with the experiment's `lab_masking_p` and `seed`). Out-of-fold predictions (for threshold tuning) and scored predictions use the **evaluation view** (as recorded, no masking). Replay (M5) replaces the evaluation view's reveals with the policy's.
4. **Build once, select folds.** Both feature tables and the targets are built once for all dev patients, aligned row by row, and folds select rows. This is safe because features are pure per patient and masking is seeded per patient (ADR-0006); a test checks that a patient's rows don't depend on the other patients in the table. Targets are attached after the features are built, and the runner refuses label or key columns among the features.
5. **Cache.** The tables are stored as parquet under `data/cache/features/` (gitignored), keyed by the cleaning, panels, features and labels configs, the chosen blocks, `lab_masking_p`, `seed` (training table only), the split fingerprint, the patient set and the source code of `sepsis.data`, `sepsis.features`, `sepsis.labels`, `eval/tables.py` and `config.py`. A cache is written to `<key>.tmp` and renamed when complete. `--no-cache` rebuilds.
6. **Model interface.** `RiskModel` with `fit(X, y, sample_weight) -> self` and `predict(X) -> raw score` (`sepsis.risk.base`). `make_model(type, params, seed)` builds a fresh model for every fit, so no state moves between folds. Every fitted statistic lives inside `fit`. `predict` never returns class labels: the alarm is `score > threshold` with the threshold tuned on the training side. `target` is `utility_diff` or `sepsis_label`; both are trained with the target weight (0 for septic hours with dt > 3). Registered types (M3-2): `dummy`, `rule_score` (B0), `logistic` (B1), `lightgbm_regressor` (B2). `MODEL_TARGETS` limits a model to the targets it can take (B1: `sepsis_label`), checked with the model type before any work. The CLI reads the `b1` section of `configs/preprocessing.yaml`, passes it to `make_model` and records it in `resolved/`, so no model reads a file.
7. **Setups.** A → B and B → A: 5-fold CV over the training hospital's stored dev folds gives out-of-fold scores, the threshold is tuned on them, and a model refit on the whole training dev part scores the other hospital's dev part. Mix: for each outer fold k, an inner CV over the other 4 folds tunes fold k's threshold, a refit on those 4 folds scores fold k, and the 5 held-out folds are pooled and scored per hospital. Every model predicts only patients it was not fitted on (tested).
8. **Partial runs.** `split.setups` may be any non-empty subset. Setups not run are `—` in the LOG, the AUROC column says `(k of 4)`, and the note says "partial run: not comparable". A partial run is never used to keep a change.
9. **Run folder.** `experiments/runs/<id>/` (gitignored): the config, the resolved configs, the feature columns, `meta.json` (git SHA, dirty flag, command, seed, cache keys and hit, scorer hash, package versions, timings), and per setup the thresholds, threshold curves, fold statistics and predictions. It is written as `<id>.partial`, renamed to `<id>`, and only then is the LOG row appended; if the append fails, the folder goes back to `<id>.partial`. So an id is in the LOG only when its run folder is complete, and after a crash the id can be rerun (the stale `.partial` is replaced). Scorer `.psv` folders are temporary. **No models are saved**: with a fixed seed any model can be refit, so replay (M5) refits.
10. **LOG row and refusals.** One row per run, appended only after every setup finished: utilities to 3 decimals, mean AUROC, `—` for labs per patient-day until replay, `eval` = `dev`. A duplicate id (exact match on the id cell) or a finished run folder is refused before any work. A dirty tree (tracked files changed, `experiments/LOG.md` excepted) is refused unless `--allow-dirty`, which adds `-dirty` to the SHA. Red flags that need no earlier run (any AUROC above `max_auroc`; A → B and B → A differ by more than `max_direction_gap`; a cross-hospital result beats mix for the same hospital) are printed and written into the note. The limits are in the `red_flags` section of `configs/protocol.yaml`. The utility-jump flag (`max_utility_jump`) compares with earlier rows, so the skill checks it.

## Note (M3-3): analyses reuse the runner
`load_dev_tables` (in `run_experiment.py`) loads the dev split, patient-hours and model tables for a config, so the CLI and the analyses (`sepsis.eval.importance`, `sepsis.eval.ordering_diagnostic`) build the same tables. `sepsis.eval.refit` refits the scored A → B / B → A model of a finished run (same config, seed, preprocessing and rows through `plan_setup` and `patient_rows`), and `check_against_run` refuses to analyse a refit whose scores differ from the run's `predictions.parquet`.

Analyses write next to the run they read, never into the LOG: `importance.csv` inside the run folder, and the ordering diagnostic's `<id>-ordering/` folder beside it.

## Note (M3-3): parallel setups and scoring
`parallel.setup_jobs` (configs/eval.yaml, `--jobs` on the CLI) runs the setups in separate processes, and `parallel.score_jobs` scores mix → A and mix → B at the same time. Each worker reads the tables from the feature cache by key and makes the same `run_setup` call as the serial path, so results are identical (a toy test compares a serial and a parallel run; `scripts/bench_scoring.py` re-scores a real run both ways). Without a cache (`--no-cache`) the setups run in turn. `meta.json` records `setup_jobs`.

## Consequences
- Every experiment is compared on the same folds, thresholds rule and scorer, and A-test and B-test are never loaded (tests patch the all-patient readers to fail).
- A repeated experiment with the same features and seed skips the table build. Any change to the configs or to the code that builds the tables gives a new cache key.
- One full experiment is 37 model fits (A → B 6, B → A 6, mix 25) plus 7 threshold tunings. On all dev patients a tuning takes about 26 s and one official-scorer call about 3 min (it writes one file per patient), so the scorer dominates a run with a fast model.
- Untracked experiment configs do not make the tree dirty; the config is copied into the run folder.
